# skills/good-question（子 skill）

## 核心哲学

**不赌用户会提问。** 用户常常不知道自己问得差——嘴上问的和心里想的不是一回事，甚至不知道自己想要什么。本子 skill 接管"把问题问清楚"这件事：分类用户的话、收敛式追问、质量自检、结束整理，全部由系统完成，不要求用户具备提问技巧。

## 何时加载

入口完成安全、隐私和范围守门后，只有同时满足下面两项才加载本子 skill：

1. 当前存在一个明确缺失的事实；
2. 该事实的不同答案会实质改变答案、适用边界、风险或下一步。

只是让用户画像更完整、表达更漂亮、回答更个性化，不足以触发追问。已有信息足够时，直接进入对应子 skill 回答。

## 工具链

- **必备**：无外部工具、API 或外部 skill。只使用当前回合中已获准处理的信息。
- **可选**：Node.js 20+ 可运行同目录 [`scripts/clarify-gate.mjs`](scripts/clarify-gate.mjs) 的判定表。用法为 `node scripts/clarify-gate.mjs --input '<JSON>'`；`missing_fact` 和 `changes_path` 为布尔输入，其余可选输入为 `safety_or_privacy`、`ambiguity_stage`、`user_response`、`question_count` 与 `new_experience`。`{}` 也是正常输入；输出为单一 JSON，包含 `decision`、`validation_signal` 与 `persistence_candidate`，不生成问题也不写入任何候选池。
- **降级**：Node 或脚本不可用时，人工按下方“追问门”和“状态”逐项判定；无法确认时保留 `UNKNOWN`，不以脚本缺失为由继续追问或猜测。

## 第一件事：分类用户的话（每次必做）

追问前，先判断用户刚才说的是哪一类，这决定缺的是什么：

| 类别 | 例子 | 缺什么 |
|---|---|---|
| 可验证的事实 | "我的 cron 昨天 12 点没跑" | 可能是更多事实（日志、错误码） |
| 对事实的解释 | "我觉得是网络问题" | 解释可能错，缺的是证据或验证动作 |
| 价值判断 | "这个方向没前途" | 缺的是判断标准，不是更多信息 |
| 想实现的目标 | "我想做内容自动化" | 缺的是具体对象/场景/验收标准 |

一句话说明你判断它属于哪类、因此缺什么，再决定是否追问。

## 追问门（收敛式，够用即停）

| 情况 | 处理 |
|---|---|
| 缺失信息不会改变处理路径 | 不追问，直接回答 |
| 缺失信息会改变处理路径 | 只问 1 个区分度最高的问题 |
| 多张候选只是表述不同，处理路径相同 | 不追问 |
| 多张候选导向不同答案、边界或下一步 | 只问 1 个能排除最多路径的问题 |
| 问题本身模糊（用户不知道选啥/要啥） | 进入收敛式追问（见下） |
| 用户回答“不知道” | 可把同一歧义改写成具体场景或反事实 1 次 |
| 改写后仍不知道 | 停止追问，保留 `UNKNOWN` |

**收敛式追问（仅当问题本身模糊时）**：

- 每次只问 1 个问题，不提前给整套问卷；
- 每问之前，用一句话说明上一条回答让你更新了什么判断；
- 优先用具体场景、反事实或极端边界来定位（"如果完全不考虑 X，你会怎么做？"）；
- 最多 3 问；信息足够立刻停，不凑满；
- 用户说"不知道"时，把同一歧义改写成具体场景 1 次，仍不知道就 `UNKNOWN`。

一个问题应能在一轮内回答。不要把多个问题用顿号、斜杠或选项列表打包成“一个问题”。

## 停止标准（什么时候算问清楚了）

满足**任一**条件即停止追问，回主流程判模：

1. **可判模**：用户补充后，已能确定走哪条主路由（knowledge／thinking／action），且缺失信息不再改变处理路径。
2. **可行动**：用户补充后，已能给出一个可观察、可回滚的下一步。
3. **到上限**：已重述同一歧义 1 次仍不知道（`REFRAME_ASKED`）→ 保留 `UNKNOWN`，停止。
4. **用户给不出**：用户明确表示不知道/不想答，且改写具体场景后仍无效 → 保留 `UNKNOWN`，停止。

停止后必须带着「结束整理」的结果回主流程，不得停在“等用户再说”的空转状态。

## 追问质量自检（问之前过一遍）

- 这个缺失信息会改变答案、边界、风险还是下一步？（说得出具体变化才问）
- 关键词是否含糊？（"自动化""优化""靠谱"——落到具体对象和动作）
- 用户默认了哪些前提？（"当然要先做这个"——前提可能正是问题所在）
- 证据来自哪里？（用户说的是亲眼所见还是听来的？）
- 有没有相反解释？（"网络问题"之外，是不是权限/超时/配置？）

## 结束整理（用户补充信息后，回主流程前）

用 3 行以内整理，然后带着它重新守门、判模：

```text
已确认事实：{用户明确提供的}
仍未验证的假设：{用户的解释中未证实的部分}
最可能改变结论的关键变量：{一句话}
```

## 输出模板

在既有的分类说明、一个区分问题（如需要）和自然语言去向后，附以下两个收尾字段：

```text
验证信号：{CONFIRMED / EXCLUDED / UNKNOWN；说明本轮追问门是否因可观察信息收敛，用户陈述本身不等于外部事实已验证}
落库候选：{YES / NO；仅当出现新的高价值区分变量、重复歧义或失败模式时标记，不能静默写入任何库}
```

`YES` 只是候选标记，不授予落库、发布或复用授权。

## 状态

- 首次区分前：`ambiguity_stage = NONE`。
- 已问首次区分问题：`ambiguity_stage = INITIAL_ASKED`。
- 已重述同一歧义：`ambiguity_stage = REFRAME_ASKED`。
- `REFRAME_ASKED` 后仍无法判断：`destination = UNKNOWN`，`question = null`。

用户补充事实后，从安全／隐私／范围守门重新开始；不静默沿用旧候选或旧裁决。

## 输出所有权

本子 skill 只拥有：

- 一句说明：为什么这个缺失信息会改变处理路径（或这个分类判断）；
- 恰好 1 个区分问题（收敛式追问时最多 3 个，逐个来）；
- 自然语言去向，例如“你补充这一点后，我再判断走哪条路径”。

不做完整诊断，不列行动清单，不查询未获准来源，不替用户猜测事实。

## 失败规则

- 无法说清缺失信息会改变什么：不追问，回主流程直接回答。
- 需要问多个问题才能开始：选区分度最高的 1 个，其余等待下一轮重新裁决。
- 同一歧义已重述 1 次：进入 `UNKNOWN`，不继续盘问。
- 收敛式追问超过 3 问仍不清晰：停止，保留 `UNKNOWN`，说明缺口。
- 用户触发安全或隐私红线：转 safety／隐私守门，不由本子 skill 继续。
