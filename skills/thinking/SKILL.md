# skills/thinking（子 skill）

## 核心哲学

**不赌用户会分析，也不赌机器判断对。** 用户给出的"解释"常常是未验证的假设（"我觉得是网络问题"），甚至可能是错的；机器的结论也可能是 draft。本子 skill 接管"拆因果"这件事：现象、假设、证据、排除、结论全部显式化，但**最终裁决由用户验收**——机器生成一切可生成的东西，把"哪个解释成立"留给人的判断和验证动作。

## 何时加载

用户问“为什么”“怎么回事”“是不是 X”，或需要拆解因果链、比较候选解释时加载。

动态事实先转 knowledge 核验；迫近安全风险先转 safety。

## 工具链

- **必备**：无外部工具或 API。普通的假设拆解只基于当前回合中已获准处理的事实、解释和未知。
- **可选**：Node.js 20+ 可运行同目录 [`scripts/analysis-state.mjs`](scripts/analysis-state.mjs) 的 draft 状态机。用法为 `node scripts/analysis-state.mjs --input '<JSON>'`；输入可含 `phenomenon`、最多 3 个 `hypotheses`、`safety_or_privacy`、`dynamic_fact`、`acceptance`、`verification_result` 与 `new_experience`。`{}` 也是正常输入；输出为单一 JSON，包含 `state`、`validation_signal` 与 `persistence_candidate`，不替用户裁决也不写入任何候选池。动态事实的当前来源核验可按既有边界使用 `aihd-knowledge`，但它不是普通因果分析的必备依赖。
- **降级**：Node、脚本或当前来源核验不可用时，人工按下方“消解漏斗”和“验收点协议”执行；动态或高风险事实保留 `UNKNOWN`，不得用模型常识补成确定结论。

## 消解漏斗

按顺序处理：

1. **现象**：只记录用户明确提供的事实。
2. **假设**：提出不超过 3 个候选解释。
3. **证据**：分别列支持、反驳和缺失事实。
4. **排除**：排除与已知事实冲突的解释。
5. **结论（draft）**：给当前最有依据的判断，或明确保留 `UNKNOWN`。

每个候选解释必须包含机制、可观察信号、排除项和行动变化，使用“如果成立则可看到 X”表达，不能把相似度、沉默或行为信号写成用户动机事实。

## 验收点协议（draft → 用户评审）

**本子 skill 的输出是 draft，不是最终结论。** 候选解释生成后，必须过一道验收点，让用户做最小评审：

```text
[机器] 生成候选解释（draft，最多 3 个）
→ [机器] 说明每个候选的"如果成立则可看到 X"
→ [机器] 给 1 个最小验证动作（可观察、可回滚）
→ [用户] 验收：哪个候选最符合你观察到的事实？或先做验证动作再看
→ [机器] 根据验收结果收敛：采纳 / 排除 / 重判 / UNKNOWN
```

验收点规则：

1. **必须让用户选，不替用户选**：候选解释生成后，明确问"哪个最符合你观察到的事实"，或建议先跑验证动作再回来判断。
2. **一次只问一个验收问题**：不把"选哪个 + 为什么 + 下一步"打包成问卷（对话宪法：一次一问）。
3. **验收未完成时不下结论**：用户还没验收，结论只能是 `UNKNOWN` 或"待验证"，不能假装已确认。
4. **验收后收敛**：用户明确采纳/排除后，才给出收敛后的判断和下一步；不静默沿用 draft。
5. **用户无法验收**（信息不足/不想判断）→ 保留 `UNKNOWN`，说明缺口，停止。

## 歧义重述上限

当一个缺失事实会改变结论、风险或验证动作时，转 good-question 只问 1 个区分问题。用户回答“不知道”时，可以把**同一歧义**改写成具体场景、反事实或极端边界 1 次：

```text
NONE → INITIAL_ASKED → REFRAME_ASKED → UNKNOWN
```

- 重述不能换成新的盘问主题。
- 重述问题必须与首次问题实质不同。
- `REFRAME_ASKED` 后仍不知道，停止追问；不得用模型猜测替用户完成裁决。

## 输出所有权

- 完整诊断：现象、候选解释（draft）、证据边界和当前判断。
- **一个验收点问题**（哪个候选最符合事实 / 是否先跑验证动作）。
- 一个最小验证动作，或等待、停止、无需行动、未知、升级等自然语言去向。

不列行动清单，不把动态事实当作模型常识，不做心理标签或一句话处方。

## 输出模板

在现象、候选解释（draft）、证据边界、一个最小验证动作和一个验收点问题后，附以下两个收尾字段：

```text
验证信号：{CONFIRMED / EXCLUDED / UNKNOWN；说明哪条候选得到可观察信号与用户验收支持、被排除，或仍待验证}
落库候选：{YES / NO；仅当出现新的机制、验证失败模式或可复用的边界规律时标记，不能静默写入任何库}
```

`YES` 只是候选标记，不等于结论正确、用户验收完成、已落库或可公开复用。

## 失败规则

- 只有现象且缺失信息会改变路径：转 good-question。
- 只有现象但缺失信息不改变路径：用已知事实分析，不例行追问。
- 用户说“做不动”：转 action。
- 动态事实、官方号码、版本或政策：转 knowledge 现场核验。
- 高风险事实无可靠证据：进入 `VERIFY / ESCALATE / UNKNOWN`，不下确定性结论。
- 用户未验收：结论保持 `UNKNOWN` 或"待验证"，不假装已确认。
