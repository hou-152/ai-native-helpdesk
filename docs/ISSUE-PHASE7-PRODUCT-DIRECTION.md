# Issue Draft：Phase 7 产品身份与结构方向

- 状态：`DRAFT / OPEN_FOR_OWNER_REVIEW`
- 日期：2026-08-19
- 性质：问题陈述与方向提案，不是发布决定。
- 一句话：**产品身份选 B（受控公共知识服务）；实现结构保持当前“A 式薄入口 + B 式受控知识服务”；未来若重构只能采用 C′，且“只治理高风险问题”不能成为减重原则。**

---

## 1. 这个 Issue 要解决什么问题

过去一段时间的证据同时指向两个方向：

- AB 自测显示：在已覆盖问题上，裸模型核心判断与人工批准卡重合 80—90%，知识卡内容边际价值低于预期；
- 19 个真实问题全部 `MISS`，说明真实覆盖不足；
- dbskill 的对照又提出一个更根本的质疑：我们是否把“薄路由 + 文件夹知识库”做成了过重的治理系统。

因此这个 Issue 不讨论“再做多少卡”，而要先回答：

> ai-native-helpdesk 的产品身份，到底是 dbskill 式工具箱，还是受控公共知识服务？
>
> 在身份确定后，实现结构才允许被修改。

---

## 2. 当前事实（截至 2026-08-19）

1. 产品身份历史一致：受控 Helpdesk，目标是推进用户问题；不是“帮用户找到文件”。
2. 公开实现已经是单一薄入口 + 按需加载 5 个 contract，不是 5 个独立子 Skill。
3. PublicCard 只解决发布资格；批准不等于正确、当前适用或解决用户问题。
4. 外部验证仍为 `0 / 30 / OUTCOME_UNKNOWN`。
5. 维护知识卡是否过贵、退回文件导航会丢失多少信任，当前没有统计。
6. 风险问题占比、治理维护成本、5 个 contract 是否独立 Skill 化，均未正式决定。

---

## 3. 钢人论证：三种身份

### A：dbskill 式薄路由 + 独立子 Skill + 文件夹知识库导航

**最强支持论证**

- dbskill 证明了一个 `SKILL.md` 就能成为可分发、可路由、可扩展的工具单元；
- 文件夹知识库随用户资料自然增长，不需要逐卡批准，增长成本低；
- AB 测试显示卡片内容边际价值低，重治理正在优化低价值环节；
- 薄结构更接近“让用户直接觉得有用”的产品体验。

**最强反对论证**

- dbskill 处理的是个人商业方法论；ai-native-helpdesk 处理的是社区公共问题和群聊隐私边界，责任不同；
- 文件夹知识库回答“文件在哪里”，不回答“这个答案是否经过验证、是否当前适用、是否可公开”；
- 完全退回 A，等于放弃来源验证、边界控制、版本锚定这三样已被 AB 测试识别出的真正差异。

### B：受控公共知识服务（治理减重，但不改身份）

**最强支持论证**

- 与仓库内真源（`SOURCE_OF_TRUTH.md`、`docs/PROJECT.md`、`SKILL.md`、knowledge contract）一致；
- 保留真正护城河：来源、边界、版本、失败处理；
- AB 测试的 Q3 已显示裸模型会给流畅但错误的答案，fail-closed 有价值；
- 减重可以在 B 内部完成，不需要改变对用户的产品承诺。

**最强反对论证**

- 若只保留身份不真正减重，B 可能成为维持现状的挡箭牌；
- 19/19 MISS 仍未回答“这个身份是否值得用户使用”；
- 治理成本与真实增量必须被测量，否则 B 只是自我确认。

### C：A + B 并存，外层薄路由和内层高风险知识卡

**最强支持论证**

- 表面上最平衡：易用的入口和受控的答案同时存在。

**最强反对论证**

- 当前 5 个下游不是独立子 Skill，前提不成立；
- “高风险才制卡”是错误原则：不是所有高风险都需要卡，也不是所有公共答案都高风险；
- C 原样采纳会制造两个未验证的结构假设。

---

## 4. 结论

- **产品身份：B。**
- **当前实现结构：保留。** 即“A 式薄入口 + B 式受控知识服务”，本轮不启动大重构。
- **未来若重构，只接受 C′：**

```text
外层保持薄入口和按需 contract；
对准备跨用户复用、公开传播的事实性答案，保留受控 PublicCard；
低风险临时分析使用明确标注的模型推理；
动态或高风险事实必须现场核验，或进入 UNKNOWN／ESCALATE。
```

- **减重原则不是“只治理高风险问题”，而是：**

```text
凡是准备作为公共、可复用答案资产传播的主张，都必须绑定来源、适用边界、版本和验证状态。
```

---

## 5. 仍然不知道的事

以下必须保持 `UNKNOWN`，不能用结论覆盖：

1. 真实用户是否认为完整 Skill 比裸模型更可信、更可执行、更想继续聊下去。
2. 维护知识卡的成本，是否真的高于文件导航丢失信任的代价。
3. 5 个 contract 是否应拆成独立子 Skill。
4. 未来问题集中高风险、版本敏感问题的占比。
5. 30 人外部验证最终是否成立；当前仍为 `0 / 30`。
