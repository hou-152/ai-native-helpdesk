# SKILL 设计哲学（2026-08-22，用户核心认知）

> 来源：2026-08-22 凌晨用户口述。这是本包所有 skill 设计的底层框架，优先级高于任何单点技巧。

## 一、Skill 的本质：不要神话

**Skill 的本质就是一段渐进式披露的 prompt（hot text）+ 运行脚本**——用文本告诉模型先做什么、后做什么。仅此而已。

- 不给它匹配工具，它什么都干不了（编排 ≠ 能力）。
- 例：给 agent 配了"每天早上报日报"的 skill，但没配搜索 API，早上它搜不了——这是 skill + 工具的问题，不是 skill 单方面的问题。

**所以：任何声称 skill 万能、skill 即一切的说法，都是神话。Skill 只做一定程度的编排与精细化适配。**

## 二、完整 Skill Pack 的四部分

真正好的 skill 必须包含四部分，缺一不可：

| # | 部分 | 说明 |
|---|---|---|
| ① | **MD 文档** | 渐进式披露的指令文本：告诉模型做什么、按什么顺序 |
| ② | **运行脚本** | 可执行的逻辑，把"说"变成"做" |
| ③ | **工具链** | 它需要的工具（API、命令、外部依赖），必须显式声明并匹配 |
| ④ | **验证机制** | validation：结尾必须验证"这次处理对不对"，并且**写库、落库** |

**只做到 ① 是 1/4 的 skill**。当前 ai-native-helpdesk 的 7 个 skill 体检结果：MD 齐全，脚本/工具链/验证落库基本缺失（详见体检记录）。

## 三、为什么 skill + 工具仍不能解决一切

因为**稳定产出需要结构化数据**。

> 结构化数据，结构化数据，is everything。

skill 只能做编排和适配；要让产出稳定、可复用、可复利，必须有结构化数据作为底层（候选池、教训库、索引、收据……）。

## 四、渐进式披露：skill 与 memory 是同构的

skill 暴露的最有价值的工程思维是**渐进披露（progressive disclosure）**：

> 在上下文关联最紧密的时刻，披露最正确的部分。

- **skill 形态**：1 个 MD 文档，相关性容易明确——写对披露顺序即可。
- **memory 形态**：1 万个 MD 文档（不同分类）——难点不再是"写对顺序"，而是：

> **在 1 万文档里如何抓选那一两句最关键的信息，加载到与当下对话最关联的内容和位置上。**

这才是最难的部分。一个文档很好驾驭，一万个文档怎么驾驭？

**推论**：ai-native-helpdesk 的判模表 = 渐进披露的路由器（在正确时刻把用户路由到正确的子 skill）；教训库 + BM25 = "1 万文档抓取"的第一版雏形；每日复盘 cron = validation + 落库的执行器。

## 五、设计检查清单（新 skill 或改 skill 时逐项过）

- [ ] ① MD：披露顺序是否写清（先做什么后做什么）？
- [ ] ② 脚本：逻辑是否可执行，还是只停留在文字？
- [ ] ③ 工具链：依赖是否显式声明？有没有给 agent 配上工具？
- [ ] ④ 验证 + 落库：结尾有没有 validation？结果有没有写库？
- [ ] 渐进披露：是否在正确时机披露正确部分，而不是一次全倒？
- [ ] 结构化数据：底层有没有数据支撑（不是纯 prompt 空转）？
