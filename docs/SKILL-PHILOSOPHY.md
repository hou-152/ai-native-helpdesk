# Skill 设计哲学

> 本文提供可迁移的 Skill Pack 设计框架。它描述能力如何被组织、执行和验证，不替代具体产品的行为契约、权限边界或发布决策。

## 一、Skill 的本质：不要神话

**Skill 是按需披露的指令文本、可执行逻辑及其运行边界的组合。**它帮助模型知道先做什么、后做什么；它本身不会自动获得工具、数据、权限或正确结论。

- 没有匹配的工具或权限，Skill 不能执行相应动作；编排不等于能力。
- 没有可核验的输入和结果，模型输出不等于处理完成。
- 因此，Skill 的价值是把适当的上下文、步骤和边界组织起来，而不是宣称可以替代工具、数据或人的判断。

## 二、完整 Skill Pack 的四部分

一个可维护的 Skill Pack 由四部分共同构成：

| # | 部分 | 作用 |
|---|---|---|
| ① | **MD 文档** | 渐进式披露的指令文本：说明触发条件、输入、顺序、输出和停点。 |
| ② | **运行脚本** | 可独立执行的最小逻辑，把可确定的判断或转换从“说”变成“做”。脚本应有明确输入、输出和可观察失败。 |
| ③ | **工具链** | 必备与可选的 API、命令、数据源或外部 Skill；同时声明工具不可用时的降级路径。 |
| ④ | **验证机制** | 用可观察信号标记确认、排除或未知结果，并给出是否产生“落库候选”的判断。 |

只提供 MD 文档的 Skill 仍然有用，但它只是完整 Pack 的一部分。运行脚本、工具链和验证机制让流程能够执行、诊断和持续改进。

## 三、稳定产出需要结构化数据

Skill 主要负责编排和适配；要让结果稳定、可复用、可比较，仍需要结构化数据作为支撑。

结构化数据可以是输入／输出 schema、状态码、索引、验证记录、版本信息或测试样本。它们应明确字段含义、来源、时效和权限边界，使后续处理可以复核，而不是只依赖自然语言回忆。

这不意味着所有结果都应自动持久化。输出中的“落库候选”只是一项标记：它提示某次处理可能包含值得沉淀的新经验、新坑或规律；是否记录、记录到哪里、何时公开，仍由相应的治理流程决定。

## 四、渐进式披露

Skill 与外部知识的共同原则是**渐进式披露（progressive disclosure）**：在上下文最相关的时刻，只加载完成当前任务所需的最小信息和工具。

- 先用入口文档判断任务类型、风险和所需能力。
- 再加载匹配的子 Skill、脚本、工具说明或结构化数据。
- 当证据、权限或工具不足时，明确停在 `HOLD`、`VERIFY`、`UNKNOWN` 或项目定义的等价状态，不用相似内容填补空白。

渐进式披露既控制上下文噪声，也使每一步的来源、权限和验证范围更容易审计。

## 五、定期复盘机制

验证不应停留在单次输出。应按固定周期或关键事件触发定期复盘，汇总验证信号与落库候选，检查以下问题：

- 哪些输入、工具或规则反复导致未知、失败或人工介入？
- 哪些候选已经有足够证据，值得进入后续评审？
- 哪些脚本、工具声明、测试或文档需要更新？

复盘可以由人工、工作流或自动化辅助完成，但“候选”不等于已记录、更不等于已批准或已发布。复盘机制的职责是形成可追溯的改进决定，而不是绕过既有治理边界。

## 六、设计检查清单

- [ ] **MD**：是否写清触发条件、披露顺序、输入、输出、停点和不做什么？
- [ ] **脚本**：可确定的逻辑是否可独立执行，并能观察到成功、失败和错误输入？
- [ ] **工具链**：必备与可选依赖是否显式声明？工具不可用时是否有不越权的降级路径？
- [ ] **验证机制**：输出是否包含验证信号（确认／排除／未知）和落库候选标记？
- [ ] **渐进披露**：是否在正确时机加载最少且相关的信息，而不是一次性灌入全部上下文？
- [ ] **结构化数据**：关键输入、结果和状态是否可被一致地记录、比较和复核？
- [ ] **定期复盘**：是否有明确的周期或事件触发条件、评审责任与改进闭环？
